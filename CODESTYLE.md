# Стиль кода OTGateway

Документ задаёт правила оформления и читаемости для всего проекта OTGateway:
прошивки, веб-интерфейса, инструментов, примеров и документации. Основной образец
C++ — `src/opentherm.cpp`. Существующий код не требуется массово
переформатировать: применяй правила к изменяемому участку, если нет явного требования переформатировать весь код в файле.

Последнее явное указание пользователя важнее этого документа. В остальных
случаях сохраняй стиль окружающего кода и учитывай приведённые ниже исключения.
Рабочие процедуры описаны в `AGENTS.md`, особенности алгоритмов и совместимости
OpenTherm — в коде, спецификации и `agent-notes/`. Изменение оформления само по
себе не является основанием менять поведение.

## Базовое оформление

- Используй два пробела на уровень вложенности, без табуляции.
- Сохраняй UTF-8 и существующие окончания строк. В `src/opentherm.cpp` — CRLF.
  Проверяй, что кириллица в документации и строках не повредилась при записи.
- Открывающая `{` находится на строке объявления или управляющей конструкции.
- У `if`, `else`, `while`, `for` и других блоков обязательны фигурные скобки,
  даже если внутри одно действие. Это относится и к JavaScript.
- После `if`, `while`, `for`, `switch` ставь пробел перед `(`; между именем
  функции и `(` пробела нет.
- Оформляй `*` и `&` по окружающему коду. В новых фрагментах `opentherm.cpp`
  используются, например, `const uint8_t* buffer` и `const auto& config`.
  Не вводи ради этого массовую правку существующих объявлений.
- Не оставляй пробелы в конце строк; файл заканчивается переводом строки.
- Не вводи произвольный жёсткий лимит длины строки. Переноси выражения по смыслу,
  когда строка становится трудной для чтения.

В проекте принято отделять следующую ветку условного блока пустой строкой,
сохраняя `} else` на одной строке:

```cpp
if (response.isSuccess()) {
  handleResponse(response);

} else if (shouldRetry()) {
  scheduleRetry();

} else {
  reportFailure();
}
```

## Пустые строки и комментарии

- Разделяй самостоятельные смысловые блоки пустой строкой, в том числе два
  соседних блока настройки задач.
- Перед комментарием, начинающим новый смысловой блок, нужна пустая строка.
  Исключение: комментарий стоит первым сразу после открывающей `{`.
- Между комментарием и относящимся к нему кодом пустая строка не нужна.
- Новые комментарии к коду пиши на английском. Объясняй причину, ограничение
  или неочевидное действие; не пересказывай очевидное присваивание.
- Не удаляй комментарии о совместимости с устройствами при упрощении кода.
- В примерах для начинающих поясняй назначение существенных вызовов API,
  даже если опытному разработчику они понятны.

```cpp
if (response.isSuccess()) {
  // Store the acknowledged value for the rest of the application.
  vars.slave.heating.indoorTemp = response.get();

  // Publish the acknowledged temperature.
  ESP_LOGI(L_OT_HEATING, "Received indoor temp: %.2f", vars.slave.heating.indoorTemp);
}
```

## Переносы строк и цепочки методов

Короткий вызов оставляй на одной строке. В длинном вызове переноси аргументы
с дополнительным отступом в два пробела, закрывающую скобку ставь отдельно.
Связанные короткие аргументы можно оставлять на одной строке:

```cpp
ESP_LOGI(
  L_OT_HEATING, "Set current indoor temp: %.2f (converted: %.2f, response: %.2f)",
  indoorTemp, convertedTemp, vars.slave.heating.indoorTemp
);
```

В обычной цепочке настройки задачи первый метод начинается на строке переменной.
Следующие методы — с новой строки и дополнительным отступом. Используй
возвращаемую ссылку `Task&`, чтобы не повторять имя задачи:

```cpp
// Read the DHW burner operating hours.
readDhwBurnerHoursTask.setInterval(60000)
  .setEnabledWhen([] {
    return isSlaveReady()
      && Sensors::getAmountByType(Sensors::Type::OT_DHW_BURNER_HOURS, true);
  })
  .onDone(onOperationDone);
openthermTaskManager.addTask(readDhwBurnerHoursTask);
```

Одиночный вызов не оформляй как цепочку с отдельно стоящим именем переменной:

```cpp
initializeSlaveTask.setEnabledWhen([] {
  return canUseBus() && vars.slave.connected;
});
```

Для сложных построителей отдельно согласовано оформление с именем
объекта на собственной строке. Сохраняй его при работе с такой цепочкой:

```cpp
request
  .setCentralHeatingEnabled(getSlaveChannelEnabled(
    vars.master.heating.enabled, settings.opentherm.heatingDisablingAction
  ))
  .setHotWaterEnabled(
    settings.opentherm.options.dhwSupport
    && getSlaveChannelEnabled(vars.master.dhw.enabled, settings.opentherm.dhwDisablingAction)
  )
  .setCoolingEnabled(settings.opentherm.options.coolingSupport)
  .setDhwBlocking(dhwBlocking);
```

Не считай это общим требованием переносить имя объекта перед любой цепочкой.
В многострочных логических условиях ставь `&&` и `||` в начале строки
продолжения. Для `if`/`else if` отступ продолжения — четыре пробела
от начала исходной строки. Если первый операнд уже вынесен на отдельную строку
внутри аргумента вызова или группы в скобках, следующие строки с `&&`/`||`
выравнивай по нему без дополнительных
двух пробелов. Группируй связанные условия скобками и не меняй их порядок
или приоритет ради выравнивания.

В многострочных `return` ставь `&&` и `||` в конце предыдущей строки,
а продолжение выравнивай под началом выражения после `return`.
Во вложенных группах также выравнивай операнды по первому выражению группы.

В многострочных логических присваиваниях также оставляй `&&` и `||` в конце
предыдущей строки, а продолжение выравнивай под началом правой части.
При длинном типе или имени переменной переноси правую часть целиком после `=`:
её базовый отступ — четыре пробела от начала объявления.

Простые условия из нескольких коротких проверок оставляй на одной строке.
Несколько `&&`/`||` сами по себе не требуют переноса; разбивай выражение,
когда это помогает читать длинные или сложные условия.

```cpp
if (!response.isSuccess() || response.getRequestCode() != 10 || response.getResponseCode() < 128) {
  ESP_LOGE(L_OT, "Boiler diagnostic reset failed");
  return;
}

return settings.mqtt.enabled && isNetworkConnected() && !isMqttBlocked() &&
       !mqttConfigureTask.scheduled() && isMqttConnected();

const bool hasOutput = activeSerial.load(std::memory_order_relaxed) ||
                       activeWebSerial.load(std::memory_order_relaxed);

const bool hasOutput =
    activeSerial.load(std::memory_order_relaxed) ||
    activeWebSerial.load(std::memory_order_relaxed);

if (prevSettings && Sensors::hasEnabledAndValid(*prevSettings)
    && (metadataChanged || !settings.mqtt.homeAssistantDiscovery)) {
  deleteConnectionDynamicSensor(*prevSettings);
}
```

## Имена и структура файлов

| Элемент | Принятый вид |
| --- | --- |
| Функции, методы, переменные, поля | `camelCase`: `readPressure`, `targetTemp` |
| Классы и структуры | `PascalCase`: `Message`, `Config`, `Float` |
| Задачи | Действие + предмет + `Task`: `writeRoomSetpointTask` |
| Менеджеры | Назначение + `TaskManager`: `openthermTaskManager` |
| Логические предикаты | По смыслу: `isSlaveReady`, `canUseBus`, `needWriteRoomSetpoint` |
| Макросы и значения обычных перечислений | `UPPER_SNAKE_CASE` по принятому API |
| Идентификаторы OpenTherm | Согласованное имя из API/спецификации: `TSet`, `Tr`, `TsetCH2` |

- Чтение ID обозначай префиксом `read`, запись — `write`. Если выделена функция,
  её имя должно соответствовать задаче: `writeRoomSetpointTask` вызывает
  `writeRoomSetpoint`, а не `setRoomSetpoint`.
- `get` уместен для получения уже имеющихся данных, например `Float::get()`.
  Имя должно давать понять, выполняется ли обмен с устройством.
- Давай имена по смыслу данных. Различай комнатную температуру, температуру
  теплоносителя, уставку, фактическое состояние и передаваемый флаг.
- Для GPIO используй `gpio`, направления — `rx` и `tx`: `rxGpio`, `txGpio`.
  Тип номера GPIO ESP32 — `gpio_num_t`.
- Не добавляй избыточный контекст к имени внутри уже понятного namespace:
  `Config`, а не `WorkerConfig`, если это общая конфигурация объекта.
- Для общей отправки сообщения используй согласованный термин `sendMessage`.
  Не возвращай неясные `exchange` и `submit` в этот API.
- Не вводи служебные `Kind`, лишние псевдонимы и сокращения без понятной задачи.
- Имена модулей проекта сохраняй в существующем виде: `opentherm.cpp`,
  `network.cpp`, `logging.cpp`; заголовки классов — по стилю соответствующего модуля.
- Группируй связанные типы осмысленными namespace и каталогами с заглавной буквы:
  `ESP32OT::Messages`, `Messages/Float.h`.
  Часто используемые общие типы не прячь без необходимости глубже:
  `ESP32OT::MessageID::TSet`.

Внутри namespace тоже нужен отступ:

```cpp
namespace ESP32OT {
  namespace Messages {
    // Message declarations belong here.
  }
}
```

Выравнивай колонки длинных перечислений и таблиц констант по окружающему коду.
Не добавляй дублирующие значения перечислений ради короткого синонима.

## Условия и поток выполнения

Для неуспешного результата предпочитай ранний выход, после которого основной
путь остаётся линейным:

```cpp
if (!response.isSuccess()) {
  ESP_LOGW(L_OT_HEATING, "Failed set current indoor temp");
  return;
}

vars.slave.heating.indoorTemp = response.get();

if (response.getData() != request.getData()) {
  ESP_LOGW(
    L_OT_HEATING, responseMismatchMessage,
    request.getData(), response.getData()
  );
  return;
}

ESP_LOGI(L_OT_HEATING, "Set current indoor temp: %.2f", vars.slave.heating.indoorTemp);
```

Ранний выход не должен пропускать обязательную последующую работу: проверку
связи, коррекцию ограничений, следующую независимую операцию или обновление
состояния. Сохраняй порядок действий исходного алгоритма.

Вложенность уместна, когда она показывает настоящую зависимость операций.
Например, ошибка необязательной записи `MaxTSet` не должна отменять следующую
обязательную запись `TSet`:

```cpp
if (settings.opentherm.options.maxTempSyncWithTargetTemp) {
  const auto response = slave.sendRequest(maxTemperatureRequest);

  if (response.isSuccess() && response.getData() == maxTemperatureRequest.getData()) {
    ESP_LOGI(L_OT_HEATING, "Set max heating temp");

  } else {
    ESP_LOGW(L_OT_HEATING, "Failed set max heating temp");
  }
}

// Send TSet even if the optional MaxTSet write failed.
const auto response = slave.sendRequest(heatingSetpointRequest);
```

Общее присваивание перед проверкой echo можно сохранить и в линейном коде
с ранними выходами; само по себе оно не требует дополнительной вложенности.

- Не заменяй все условия одним шаблоном автоматически. Выбирай структуру,
  которая ясно показывает зависимости и сохраняет побочные эффекты.
- Предпочитай обычный `while` конструкции `for (; condition; ...)`.
- Не строй большие `switch` для ручной диспетчеризации ID или шагов, если
  операции естественно выражаются отдельными задачами.
- В небольших учебных примерах, например Slave, `switch` по ID уместен.
  Ветви одного уровня оформляй одинаково: `if / else if / else`, с `break`
  для завершения `case`. Не смешивай без причины выход из `case` и всей функции.

## Функции, типы и абстракции

- Для локальных функций и данных `.cpp` используй `static`, а не анонимный namespace.
- Не добавляй `inline` только потому, что функция короткая. В `.cpp` это не нужно
  для выбора оптимизации компилятором; в заголовках учитывай ODR и способ определения.
- `this->` необязателен. Не добавляй без необходимости (конфликтов).
- Небольшую функцию, вызываемую только одной задачей, можно встроить в callback.
  Содержательный повторно используемый алгоритм оставляй отдельной функцией.
- Callback, используемый один раз, обычно записывай лямбдой на месте регистрации.
  Общий `onDone` нескольких задач может быть отдельной `static` функцией.
- Никогда не объявляй лямбды и callbacks в заголовках `if`, `for`, `while`.
  Вызов с callback записывай отдельным выражением; в условии проверяй результат.
- Не создавай обёртку, класс, файл, диспетчер или таблицу только ради структуры.
  `constexpr`, шаблоны, наследование и контейнеры должны давать конкретную пользу.
- Используй `const` для неизменяемых данных. `auto` подходит, когда тип очевиден
  из вызова; явный тип нужен там, где он поясняет формат или единицы данных.
- Выбирай тип по данным: фиксированную разрядность для бинарных полей протокола,
  `gpio_num_t` для GPIO. Не вводи динамическое выделение там, где хватает значения.
- Не применяй `std::move` к обычному `float` и не усложняй владение без причины.
- Не дублируй состояние, проверки и парсинг, уже представленные в библиотеке,
  `settings` или `vars`. Отдельный флаг нужен только для отдельного состояния.
- Сохраняй экономное использование flash и heap: общие строки в `strings.h`,
  минимум лишних копий и частых выделений памяти. Рост динамических буферов
  должен быть обоснован и ограничен по потребностям задачи.

## Оформление задач

- Перед каждым самостоятельным блоком добавления задач в менеджер пиши короткий
  английский комментарий о назначении блока.
- Простые условия включения — поддержка функции, наличие датчика, готовность
  устройства — размещай в `setEnabledWhen`, если нет отдельной причины проверять
  их внутри тела. Не дублируй одно и то же условие механически в двух местах.
- Повторная проверка состояния оправдана, если оно могло измениться во время
  блокирующей операции или определяет завершение последовательности.
- Настраивай период через `setInterval`. Не добавляй второй ручной таймер для
  того же ограничения частоты. Время успешного ответа или потери связи может
  иметь самостоятельный смысл и не является таким дублем.
- Не добавляй `resume(delay)` по шаблону: период задачи и отложенное возобновление
  имеют разное назначение. Проверяй семантику используемой версии библиотеки.
- Не рассчитывай, что `forceRun()` проверяет `setEnabledWhen`: в используемой
  Mycila он обходит условия. Для условного запуска ONCE нужен корректный вызов
  с учётом её pause/resume, например `resume().tryRun()` или явная проверка:
  ```cpp
        if (readModulationTask.idle() && readModulationTask.enabled()) {
          readModulationTask.forceRun();
        }
  ```
- Не вводи ручной арбитраж, массивы шагов или систему приоритетов, когда достаточно
  последовательного менеджера, интервалов и предикатов.
- Для обычных запросов внутри OpenTherm-задач используй понятный синхронный код.
  Не превращай его в цепочки callback с большим `switch` только ради асинхронности, если это не влияет на производительность.
- Изменяй задачу через её изменяемый объект. Параметр `const Mycila::Task&`
  в `onDone` нельзя использовать для вызова неконстантного `setInterval`.

Это правила читаемости, а не разрешение менять периоды, порядок операций или
условия управления устройством. Такие изменения требуют отдельного основания.

## Сообщения и логи

- Используй готовые типизированные Message-обёртки для сборки и разбора данных.
  Не собирай raw вручную, чтобы затем сразу завернуть его в подходящий тип.
- Обёртка содержит функциональность своего формата/ID. Избыточное уточнение типа
  в методе не нужно: `Float::get()`, а не `Float::getFloat()`.
- Доступ к raw сохраняй для низкоуровневой работы и логирования. Не создавай
  автоматическую фабрику подклассов, `variant` или полиморфную диспетчеризацию,
  если вызывающий код всё равно вручную выбирает формат и это не даёт другой пользы.
- Различай ошибку обмена и несовпадение подтверждённых данных. Для mismatch
  используй понятный текст с ожидаемым и полученным значениями.
- Общий формат повторяющегося сообщения выноси в общую строку/константу.
  Форматные спецификаторы должны соответствовать фактическим типам аргументов.
- Значения, нужные остальному проекту, сохраняй в соответствующих полях `vars`.
  Не меняй порядок сохранения и проверки ответа только ради красивой ветки.
- При сравнении `float` выбирай допуск по физическому смыслу величины. Если
  требуется точное совпадение переданных данных, используй их кодированное
  представление, когда это предусмотрено логикой.
- Не помещай пароли, токены, секреты и приватные конфигурации в диагностические сообщения.

## Примеры, веб-код и документация

- Примеры показывают простой основной путь использования API. Избегай служебной
  «магии», ручных счётчиков, флагов ожидания и скрытых требований к порядку вызовов,
  если библиотека уже предоставляет нужный механизм.
- Поясняй неочевидные проверки результата, например зачем нужен `hasFrame()`
  в обработчике статусов, допускающем завершение без принятого кадра.
- В примерах с GPIO-настройками через build flags, как TransparentProxy,
  используй защищённые `#ifndef` значения по умолчанию. Вложенные директивы
  оформляй с отступом:

```cpp
#ifndef BOILER_RX_GPIO
  #define BOILER_RX_GPIO GPIO_NUM_35
#endif
```

- Не переноси в основной код предположения, допустимые только в демонстрации,
  например безусловный `Serial.printf` из callback.
- HTML, CSS и JavaScript оформляй читаемо с отступами окружающего файла;
  минификация выполняется при сборке. Для JS действуют те же требования к скобкам
  и смысловому разделению блоков.
- Для недоверенного текста используй `textContent`/`setTextValue`. Вставка HTML
  должна быть необходима по смыслу и учитывать происхождение данных.

## Перед завершением правки

- Сверь изменённый участок с окружающим кодом и последними указаниями пользователя.
- Проверь отступы, пустые строки, переносы цепочек, комментарии и окончания строк.
- Убери случайное переформатирование посторонних участков.
- Убедись, что сокращение кода не изменило порядок действий и обязательные ветки.
- Не добавляй правила, абстракции и исключения, не нужные для решаемой задачи.
